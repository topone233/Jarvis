# Jarvis

（**J**ust **A** **R**ather **V**ery **I**ntelligent **S**ystem 只是一个相当聪明的智能系统）

## 定位

服务于我个人的本地ai助手，b/s架构，只考虑windows下使用。个人内网使用不需要被安全束手束脚。

1、Memory和Knowledge不应该完全等价，2、不要叫 Memory Retrieval  而是 Context Retrieval。3、Compact 的结果不是一个 Summary，而是一次“信息生命周期迁移”  。4、保留Provenance 。

## 上下文管理

在有限的上下文窗口里面，持续地、可控地去服务好每一次对话。

把"信息的生命周期"作为第一设计原则。越稳定的东西越应该被当作代码来管理，做版本化、缓存优先。越易变的东西越应该被当作数据来处理，做检索、压缩、按需注入。

### 背景：为什么需要动态 Prompt 系统

第一个瓶颈，上下文窗口是有限的，但用户的历史却是无限增长的。你不可能把一个用户所有的历史对话原文，都给塞进每次请求里面去。

第二个瓶颈，不同信息的时效性差异特别大。系统规则可能几个月都不变，但用户当前的对话每秒都在变化。你要是把它们混在一起管理，就会导致缓存失效，维护起来也很困难。

第三个瓶颈，成本和延迟的问题。你不做检索、全量注入的话，就意味着每次请求都要去处理大量的 token。推理又慢又贵，这个代价是很高的。

### 整体架构：四层模型

设计动态 Prompt 系统的核心思路，说白了就是分层解耦。把不同生命周期、不同来源的信息拆开来管理，然后在推理的时候按需去进行组装。

核心矛盾是什么？如何在有限的上下文窗口里面，给模型喂进去"当前这一轮最需要的信息"，而不是把"所有信息"都一股脑塞进去。给不同生命周期的信息找到合适的存储方式和检索方式，而不是把所有东西都塞进同一个字符串里面。

- L1 System/Instruction（指令层）：静态,版本化,长期不变

  角色设定、行为准则、输出格式约束、还有工具的 schema，都放在这一层。

  有一个很重要的点，这一层应该是"代码"，不是"数据"。也就是说，它应该由工程师或者产品来维护，可配置和版本管理，而不是在运行时去拼接字符串。

  如果复杂的话，可以把这一层拆成多个可以组合的 sub-prompt 模块。然后按场景去动态勾选组合。

- L2 Persistent Memory（记忆层）：跨会话持久化,增量更新

  这一层是跨会话持久化的，可以再细分成三种粒度。

  第一种是 Profile，也就是结构化的数据。比如姓名、角色、长期偏好这些 key-value 或者小 JSON。体积比较小，可以常驻在那里不用去检索。

  第二种是 Semantic Memory，也就是语义记忆。用户说过的事实、做过的决定、项目的状态这些，适合用向量化来存储，然后按 query 去进行检索。

  第三种是 Episodic Memory，也就是情景摘要。历史会话的摘要记录，按时间或者主题来索引，用来"回忆某次对话"。

  这三种粒度对应着不同的读取策略，具体可以看下面的"检索策略"部分。关键是什么？关键是不要全量塞进 prompt 里面，而是要像 RAG 那样按相关性去检索、按需去注入。

- L3 Session Context（上下文层）：单会话内动态,随对话增长

  当前会话的原始或者半原始的对话历史，工具调用的记录和结果，检索增强的内容（也就是 RAG 召回的文档片段），还有当前时间、地点这些运行时信息。

  这一层是体积增长最快的，也是最需要去做压缩管理的部分。它的生命周期，会随着会话结束或者窗口滚动而失效。

- L4 Turn-level Ephemeral（单轮临时层）：单轮临时,用完即弃

  用户提问、ai回答，本轮工具调用的临时结果

### Memory 的读写分离设计

#### Memory Write

关于触发的时机，常见的有三种模式。

第一种是实时触发。检测到关键信息的时候就立即写入，比如用户说"我叫XX"、"我更喜欢简洁回复"这种。延迟比较低，但是，很容易写入噪音。

第二种是会话结束触发。整个会话结束之后，用一次"总结 LLM 调用"来提取值得记住的事实，然后批量写入。质量会更高一些，但是有延迟。

第三种是定期离线触发。类似于定时任务，批量处理最近的若干会话，去做去重、合并、压缩这些操作。

**实现取的路线**（2026-09-14 定，2026-09-17 改为原生 tool call）：判断"要不要记"搭主回复的车，不做单独的提取调用。请求注册 `save_memory` / `forget_memory` 两个工具，模型在一次回复里同时给出正文和 tool_calls（OpenAI Chat Completions 语义，流式时文本 delta 与 tool_calls delta 并行），仅在这轮确实有值得记或需要忘的内容时才调用；不回传任何 tool result，后端在回答完成时执行参数落库，正文流式显示、所见即所得。没有动作就没有任何额外调用，"写入记忆"步骤也只在真有动作时出现在执行步骤里——一条普通的 hi 不再为它花 4 秒。对话里让 AI 删记忆（"忘掉……"）走同一条路：模型看得见「记忆」列表，forget 的 key 与 content 都从列表原样复制即可，删掉的记忆进记忆页的「已删除」可找回。

写入之前还需要做一层过滤。

首先是事实性和推测性的区分。只写用户明确陈述的内容，不要写 AI 自己推断出来的。比如"喜欢简洁"这是陈述，"可能是内向的人"这就是推测了，后者不应该写进去。

还有就是去重和合并的问题。新事实和旧事实冲突的时候，比如职位变更了，是覆盖、追加历史、还是保留两者打上时间戳，这些都需要有明确的策略。

#### Memory Retrieval

不能全量注入，要按需去检索。不然的话，token 成本会失控，而且无关信息会干扰模型的注意力，导致回答质量下降，这就是所谓的"lost in the middle"问题。

关键词或者结构化匹配，适合那种小而确定的 profile 数据，直接按 key 去查就行了，比如"用户名字"这种。

向量检索，也就是 Embedding 加 ANN，适合语义记忆。把当前 query 向量化，然后召回 top-K 相关的记忆片段。

元数据过滤加向量检索的混合方式，先按时间、类别、标签去过滤，再做向量排序。这样可以避免语义相似但已经过期的信息被召回。

还有一种是 LLM 自主检索，也就是 agentic memory。让模型自己决定要不要去调用"搜索记忆"这个工具，而不是每次都强制注入。这种方式比较灵活，但是会多一次推理的延迟。

关于相关性判断的实践技巧，有这么几点。

不要只用相似度分数一刀切，可以加上"新鲜度衰减"，越新的记忆权重越高。

还可以加"确认次数"的权重。用户反复提到的事实，比只说过一次的要更可信。

还可以加一个信号，就是"该记忆在当前任务类型下，历史上是否被有效使用过"。

### 组装（Assembly）阶段的设计

第一个坑，把所有历史对话都塞进 context。这样会导致成本爆炸，而且模型的注意力会被稀释。一定要做压缩或者检索，不能"记住一切"。

第二个坑，检索只看语义相似度，不考虑时效性。这样会导致召回过期的信息。比如用户半年前说"在学 Python"，现在可能早就转方向了。

第一个建议，用模板引擎而不是字符串拼接。

第二个建议，边界隔离与防注入：组装的时候，不同来源的内容一定要有清晰的结构标记（2026-09-17 定：不用 XML 标签，改用 Markdown 小节标题——## 记忆 / ## 历史摘要 / ## 知识资料，压缩输入同理）

###### 长对话压缩策略

第一种是滑动窗口。只保留最近 N 轮的原文，更早的就摘要化。

第三种是分层摘要。短期用原文，中期用摘要，长期用"摘要的摘要"，类似于指数衰减。

第四种是关键事件锚定。识别对话中的"决策点"，比如做了什么决定、给出了什么承诺。这些是不能被压缩掉的，其余的闲聊内容可以大幅压缩。

## 知识库

通过对话，记录我的灵感、笔记、文档素材等。一方面是我自己可以检索、回顾、可视化。另一方面是我的ai助手，可以和我一起成长，记住我的知识、经验、喜好等。

记忆、知识等要记录原始内容，支持删除。通过页面手动操作或者ai对话智能操作。

## 技能（Skills）

工具能力层：安装遵循通用 Agent Skills 规范的技能（`SKILL.md` + YAML frontmatter 的
name/description，可带 scripts、references），与 Claude Code、Codex 完全通用，与
Jarvis 不耦合。

- 存放：数据目录 `skills/` 下，导入即整棵复制，原文件夹随后的变动不影响已导入副本。
  不放代码目录——数据目录是「换一个 = 另一套数据」的完整单元。
- 触发两条路：对话里输入 `/技能名` 直接注入技能全文（不花模型回合），或模型看系统提示词
  里的 `## 可用技能` 清单后经 `skill` 工具自行 load / run。
- 脚本：skill 自带的脚本可以执行，以技能目录为工作目录；支持 .py / .ps1 / .bat / .cmd，
  120 秒超时、2 万字符输出上限，无沙箱。
- 启停：设置 → 技能 tab，卡片式（名字 + 开关 + 描述），默认开启；停用状态存设置 KV
  的禁用名单，无键即全开。

## 系统工程

亮眼差异化：

- 可解释：每个建议附理由和证据。
- 可反馈：一键点赞/点踩/重新生成，越用越准。
- 可审计：每个Agent的决策和行动日志应被完整记录和展现，形成清晰的审计追踪

Slash 命令：`/compact` （到阈值自动压缩、主动用/命令压缩、通过自然语言对话压缩）等。

## UI

实现一个类似 chatgpt.com 的对话界面，风格向chatgpt.com看齐，浅色主题，整体简洁、柔和不锋利不僵硬、自然清新。使用内联svg图标，不依赖外部图标库。整体风格统一，不要有刺眼、不协调的配色或内容。只考虑PC端。

  - 第一区域：新聊天（方形 + 铅笔的编辑图标）、定时任务（时钟图标）
  - 第二区域：项目（文件夹图标），右侧有 `+` 新建按钮（默认隐藏），可重命名、删除、置顶

  - 底部：头像、用户名、记忆入口（书签图标，打开记忆页：查看 / 编辑 / 删除，下方折叠「已删除」可恢复或永久删除）、设置按钮（省略号图标）

    - 回复区域的下方：左侧：点赞、点踩，右侧：复制、重新生成按钮。

  消息不单独删除。删除的单位是左侧栏里的一次对话，会话内不提供删除入口，这样一轮问答不会出现只剩一半的状态，重新生成也就可以假定最新一条回复一定在。对话级删除是**永久删除**（2026-09-14 定，取代早先的回收站语义）：消息、run 日志、审计事件、压缩记录、点赞点踩一起物理删除，删错无法恢复。

### 反馈

toast 只接「做完之后屏幕上什么都不剩」的操作：删了对话、删了模型配置、把某条配置设为默认——行没了或者徽标挪了位置，不说一句就不知道东西去哪了。

屏幕上还看得见的，不要 toast。发消息本来就看得见消息，保存提示词旁边就有「已保存。」，复制会把按钮变成一个对勾。这些再飘一条，等于用第二个声音把同一句话再说一遍。

失败留在原地，跟着出问题的那个东西一起显示，不要飘走——用户还得对着它做点什么。

`alert` 和 `confirm` 一概不用，不是嫌它们难看，是它们会把整个页面冻住：流式回复和正在收的 SSE 都活不过那一下。

### 一次回复的生命周期

这一节是硬要求，直接决定用起来顺不顺手：刷新页面、切走标签页、关掉浏览器再打开，回复都必须还在。还在生成就接着流式显示，已经生成完就直接显示结果，而这两种情况前端的渲染路径是同一条——结束的那次是一条 `message.completed` 带全文，不需要为"错过了"写分支。

重连的做法：把 `run.started` 里的 `run_id` 存下来（助手消息上的 `metadata.run_id` 是同一个值，刷新后可以据此找回）。回来先 `GET /api/runs/{run_id}` 问这个 run 还在不在跑，在跑就 `GET /api/runs/{run_id}/stream` 接上。文本是累积快照，客户端唯一要记的状态是"已经渲染了多少字"，所以接上既不会重字也不会漏字。生成中的界面状态（终止按钮、进度条、光标）也要一起恢复。

后端被关掉时（比如关机），没跑完的 run 会在下次启动时被标成 `interrupted`，重连拿到的是一条 `run.failed` 加一句说明。这种情况下前端要**明说这一轮被中断了**，把已经拿到的部分照常显示出来，但不能把半截回答伪装成完整回答，也不能让用户对着一个永远不动的光标等下去。接下来是重新生成还是继续追问，由用户决定。
